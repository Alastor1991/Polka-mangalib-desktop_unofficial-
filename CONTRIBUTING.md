# Как участвовать

Спасибо, что хотите помочь Полке. Перед началом прочитайте [docs/architecture.md](docs/architecture.md): там описано, как устроен код и какие гарантии держит каждая часть. Что сейчас в работе и что делать дальше, сведено в [docs/roadmap.md](docs/roadmap.md).

## Сборка и проверки

```sh
cargo build
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

CI на каждый пуш делает то же самое, и PR с красной сборкой не принимается.

Живые проверки против настоящего API лежат отдельно и помечены `#[ignore]`:

```sh
cargo test -p libsocial -- --ignored --test-threads=1
```

Запускайте их, когда меняете что-то в работе с API. Гонять их в цикле не надо, это нагрузка на чужой сервис.

## Правила, которые не обсуждаются

1. Платный контент не обходится. Закрытые главы и ранний доступ открываются только тем, кто купил их на своём аккаунте. PR, который это меняет, будет закрыт.
2. Сервис не перегружается. Не убирайте ограничение частоты, повторы с паузой и паузы загрузчика, не поднимайте параллельность сверх 8. Скорость ищите в кэше: число запросов к сервису увеличивать нельзя.
3. Чужие плееры не вскрываются. Kodik открывается в браузере, его потоки мы не достаём.
4. Клиент не выдаёт себя за другие приложения: свой `User-Agent`, никаких чужих `client_id`, кроме публичного веб-клиента сайта и клиента, который выдадут Полке сами разработчики сервиса.
5. В репозиторий не попадает чужой контент и личные данные: страницы глав, токены, ники пользователей в фикстурах. Ответы, снятые с вошедшего аккаунта (закладки, история, переписка, друзья, настройки), не переносятся в фикстуры даже обезличенными: фикстуры для них пишутся вручную по устройству настоящего ответа.
6. Логика пишется в ядро. Интерфейс будет переписан на Slint, поэтому всё, что можно написать без виджетов, живёт в `crates/polka-core`, а окно только рисует. Новые возможности в окно iced не добавляются.

## Как устроить изменение

- Новый запрос к API: метод в модуле своей области в `crates/libsocial` (карта модулей в [architecture.md](docs/architecture.md#карта-модулей)), правила ниже. Снимите настоящий ответ (`polka dev-get <сайт> <путь>`), уберите из него поля просмотра и ники, положите в `crates/libsocial/tests/fixtures` и напишите тест разбора. Опишите запрос и его ловушки в [docs/api.md](docs/api.md).
- Логика клиента (повторы, зеркала, токен) проверяется на мок-сервере в `tests/client.rs`, без сети.
- Загрузчик проверяется так же: задания целиком на мок-сервере в `job_tests` в `crates/polka-core/src/downloads.rs`. Если меняете поведение очереди, паузы, удаления или докачки, добавьте туда сценарий.
- Схема базы меняется только новой миграцией в конце `MIGRATIONS` в `crates/polka-core/src/db.rs`. Старые миграции не трогайте: они уже применены у пользователей.
- Интерфейс проверяйте глазами. Запустите окно на нужном экране (`POLKA_DEV_OPEN`, `POLKA_DEV_TAB`) с отдельными каталогами данных, чтобы не трогать свою библиотеку:

  ```sh
  XDG_DATA_HOME=/tmp/polka-dev/data XDG_CACHE_HOME=/tmp/polka-dev/cache \
  POLKA_DEV_OPEN=mangalib:7965--chainsaw-man:0 cargo run
  ```

## Как писать модуль libsocial

- Методы клиента – `impl Client` в модуле области. Запросы идут через общие методы `Client`: `get_data`, `get_json`, `send_data`, `send_ok`, `send_raw` (ответ целиком), `send_record` (запись в ответе с обёрткой `data` или без), а особые случаи (multipart, свои заголовки) через `send_api`. Отдельных обёрток под сайт не заводите: сайт задаёт `Site` в аргументе. `path` без `/api` и без ведущей косой: `"notifications/count"`.
- `Site` в запросе – тот, от имени которого спрашивает сайт. Если ответ от `Site-Id` не зависит, берите `Site::MangaLib`.
- Модели терпимые: поля, которые сервер присылает то числом, то строкой, то `null`, разбираются через `serde_util` и `listing` (`u64_lenient`, `opt_u64_lenient`, `string_lenient`, `null_default`, `lenient_vec`, `bool_lenient`) и `#[serde(default)]`. Элемент списка, который не разобрался, выбрасывается, а не валит страницу. Большие объекты, которые пока не нужны, держите как `serde_json::Value`.
- Параметры-перечисления (сортировки, фильтры) – Rust-енумы с методом, который даёт строку для query. Значение «все» сервер обычно отвергает, его не отправляют вовсе.
- Если сервер точно ответит 422 (чужая сортировка, слишком короткий поиск), откажите до запроса через `Error::Other` с понятным текстом.
- Форматированный текст отдавайте как `rich::Doc` (`Doc::from_html`, `Doc::from_prosemirror`) и оставляйте сырую строку в модели.
- `libsocial` не пишет на диск и не держит состояния, кроме сетевого.
- Тесты: на мок-сервере для каждого запроса на запись проверяются путь, метод и тело (`body_partial_json`); для чтения – разбор модели и подсчёт страниц. Живые проверки на чтение без входа – функции с `#[ignore]` в том же файле тестов. Запросы на запись к настоящему API из тестов не отправляются никогда.

## Тесты на своём аккаунте

Иногда запрос на запись нужно проверить на настоящем сервере. Тогда:

- проверяйте на своём аккаунте и по одному запросу, руками, не из тестов;
- перед записью прочитайте текущее состояние и после проверки верните его. Сервер часто обновляет запись молча: `POST /bookmarks` на тайтл, который уже в закладках, перезапишет его папку и место, ответив 200 вместо 201;
- берите для проверки тайтлы, которых нет в ваших закладках;
- публичные действия (комментарии, отзывы, голоса за чужое) видны другим людям: делайте их только если готовы к этому и сразу убирайте;
- токен из хранилища не печатайте и не сохраняйте в файлы.

## Код

- Комментарии и сообщения пользователю пишутся на русском.
- Комментарий объясняет, зачем код устроен именно так. Пересказывать код словами не нужно.
- Ошибки, которые видит пользователь, говорят, что случилось и что делать, без служебных подробностей.
- Токены и пароли не попадают в логи, `Debug` и сообщения об ошибках.
- Длинное тире (U+2014) в тексте проекта не используется: ни в коде, ни в комментариях, ни в документации. Ставьте короткое `–` или перестраивайте фразу. Исключение – данные сервиса в фикстурах: их не правят.
